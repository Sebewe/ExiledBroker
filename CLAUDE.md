# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ExiledBroker is a Path of Exile 1 market tool: historical and live exchange data → league-start price patterns, arbitrage (card turn-ins, Chaos↔Divine loops) and, later, predictions. `README.md` and `docs/` are the project's **living design documents**: the README's Status table, Next steps and layout, plus `docs/decisions.md` (decision log by topic, dated), `docs/data.md`, `docs/hosting.md` (cost issues, performance findings), `docs/findings.md` and `docs/roadmap.md`. Read the relevant doc before larger changes and update it with them; keep the README short and put detail in `docs/`.

## Be very polite to GGG and poe.ninja (non-negotiable)

GGG's and poe.ninja's public endpoints are a courtesy, and both blacklist clients that get overzealous. Being blocked would kill the project: there is no other source for this data. Treat every request to their servers as a cost to avoid.
- **GGG is the one to be careful with; poe.ninja tolerates more** (the user, 2026-10-24). Fetching poe.ninja's economy endpoints (new lists, a one-off batch) doesn't need asking first. It still goes through `PoliteClient`, conditionally where possible, and you say how many requests it made. Everything below stands for GGG as written.
- **Never re-download what we already have.** Exchange hours are immutable: fetch each once, ever. Reference data goes through `reference.fetch_if_changed` (conditional requests, at most every `max_age`). Before writing anything that fetches, check how it decides what's missing. It must come from the database or a completed file, not "fetch the window again". A rebuild (`--force`, a `LOADER_VERSION` bump) reads pages already on disk and fetches only the missing ones (`fetch_page`). The hosted pipeline keeps the live window's pages in Postgres (`exchange_page`, `EB_EXCHANGE_PAGES=database`), so a rebuild there re-reads them. A new server is seeded from the local copy (`eb site seed --hosted`), never backfilled from GGG: `eb pipeline run` refuses an unseeded database.
- **Every request goes through `ingest/http.PoliteClient`**, the internal rate limiter: one request at a time, at least `request_min_interval` (1 s) apart, exponential backoff with `Retry-After` honoured on 429/5xx, and a User-Agent naming the repo. Never call `httpx`/`urllib` directly, never parallelise requests (no threads, async fan-out or several clients at once), and never lower the interval to make something faster. Use one client per command, so spacing holds across the whole run.
- **Poll no faster than the data changes:** one exchange hour per hour, a few minutes after it's published; poe.ninja no faster than its ~15-minute refresh. A 429 means slow down for good, not retry harder.
- **Tests and development never hit the real servers.** Use `FakeExchange` / `client_for()` and the recorded fixtures. Don't run ad-hoc probes or loops against the live endpoints to explore. Use pages already on disk, and ask the user before any one-off request batch.
- **Count the cost.** Any new fetching code reports its requests (`ingest_run`, `tests/test_performance.py`), and a change that adds requests says how many and why.

## Supabase is only the off-site backup: conserve its egress (non-negotiable)

The site runs on Railway (web, Postgres, the pipeline cron, on a free private network). Supabase's free tier holds an off-site copy of the site's database (`docs/supabase.md`): after each pass the pipeline syncs to it (`storage/backup.py`), uploading the changes and reading back ~25 kB. Supabase bills what's read out of it (5 GB a month free), not what's written in, so **nothing reads from Supabase except the pipeline's hourly sync, and a restore** (`eb site restore`, the one bulk read: ~300 MB, behind `--yes`; with the local copy at hand, `eb site seed --hosted` restores for free).
- **Development and tests use local resources only:** the local DuckDB, the compose `db` Postgres, the Railway simulation's Postgres and `backup` containers, a throwaway Postgres container for `EB_TEST_POSTGRES_URL`. Never point `EB_DATABASE_URL`, `EB_TEST_POSTGRES_URL`, `eb serve`, the simulation or a load test at Supabase; `EB_BACKUP_URL` is set only on the hosted pipeline. `tests/conftest.py` blanks `EB_DATABASE_URL` and `EB_BACKUP_URL`; keep it that way. The connection string lives outside the repo (`../.env.supabase`) and is never loaded automatically.
- **Profile and measure locally**, on local Postgres databases seeded with the same data (a byte-counting relay in front of the backup's). Touch Supabase only for a deliberate, small check the user has asked for, and say what it will cost first. **Supabase MCP queries** read from it too: small metadata queries only (sizes, counts, advisors), never row dumps.
- **A sync must stay incremental:** it reads which hours and pages the backup has (compact strings) and a few checksums, never rows. `tests/test_backup.py` budgets a pass's reads from the backup; a change that adds reads says how many bytes and why. A league rebuilt by a new `LOADER_VERSION` is emptied and given back its space (`VACUUM FULL`) before it's copied again, so the 500 MB plan isn't doubled.
- **Seeding Supabase by hand** (`eb site seed --hosted` at it) is upload, which is free, but only when the user asks, and empty its tables first (the user runs the TRUNCATE in Supabase's SQL editor; auto mode blocks it).

## Never sit in a prompt waiting on a long run (non-negotiable)

The user's words (2026-10-24): don't run an extended script that takes hours while in the prompt. It's excessive, it delays everything and it burns their tokens. A 30-minute prompt spent waiting on one bash command is the failure this rule exists to stop.
- **Anything expected to take more than 5 minutes runs outside the session:** a full ingest or `exchange sync`, `eb live sync`/`watch`, `launch picks`, `backtest run`, a long rebuild, the Railway simulation, a load test, or any script with intended delays (polite spacing, sleeps, polling). Hand the user the command to run themselves (e.g. `scripts/ingest.sh …`, which logs to `data/logs/latest.log`), or start it detached (`nohup … > data/logs/<task>.log 2>&1 &`), then end the turn and say how to check on it and stop it (`pkill -f "eb "`).
- **Don't wait on it in the prompt:** no foreground runs with long timeouts, no `sleep`/Monitor/until-loops, no repeated `tail`s of the log to watch progress. Pick the work up when the user comes back with the result.
- **Estimate before running.** If you can't tell how long something takes, assume it's long: count the requests (1 s apart, so 3,600 pages is an hour) or the rows, or try it on one league or a small slice first. Prefer the quick checks (one test file, one league) over full runs while iterating.

## Architecture

**Pipeline writes, UI reads.** CLI jobs (`cli.py` → `ingest/` → `normalize/`) fetch data and write a local DuckDB file (`data/exiledbroker.duckdb`) plus Parquet. The site (FastAPI in `api/`, React in `web/`) only reads, and only through `services/`; its one write is the cookie-free usage counts (`api/usage.py`, `docs/usage.md`: a few upserts every 5 minutes, nothing stored about visitors). (The Streamlit demo was retired on 2026-10-22; it's in git history.)

**The site's database** is Postgres when `EB_DATABASE_URL` is set (Railway's Postgres hosted, the compose `db` service locally), else the local DuckDB file. DuckDB stays the research database (all history); Postgres holds only what the site reads (the live league).
- `db.site_session()`: the API's reads (pooled psycopg). `db.site_writer()`: `eb live watch`'s writes when `EB_DATABASE_URL` is set, an in-memory DuckDB with Postgres attached (`USE site`), so the incremental loader runs unchanged and its transaction is Postgres's. Code that takes `settings` uses these or `settings.db_path`, never a default path.
- `eb site seed` copies leagues' site rows, the Launch history and picks from DuckDB into Postgres; `--hosted` also copies the loaded hours' raw pages, for a new server. Hosted, `eb pipeline run` (`ingest/pipeline.py`) writes Postgres directly through `site_writer`: no DuckDB file and no disk. It keeps only the live window's pages (`cx.prune_pages`), captures a finished league into the Launch history (`launch_picks.refresh`) and drops a replaced league (`site.drop_leagues`). Then, with `EB_BACKUP_URL`, it syncs the site's database to the off-site backup (`storage/backup.py`: `sync(src, dst)` mirrors a site database whole, or the local copy's named leagues; it reads from `dst` only which hours and pages it has). A failed backup is reported on the pass's line, never raised. With `EB_HEALTHCHECK_URL` the pass pings a dead-man's switch (`ingest/healthcheck.py`: `/start`, then success, or `/fail` when it raised, the backup failed or the feed is stale; a ping never fails the pass; `tests/conftest.py` blanks it).
- **API** (`api/routes/*`): thin wrappers over services with pydantic response models (the frontend's TS types come from the OpenAPI schema). Results are cached in a bounded LRU (`api/cache.py`) keyed on the data version (`max(ingest_load.loaded_at)`), so they're recomputed once per load. Timestamps go out as UTC; NaN/inf as null. Unknown league 404, bad args 422, no data yet 503.
- **Frontend** (`web/`): React + Vite + TypeScript. Types come from the API (`web/openapi.json` → `src/api/schema.d.ts`; `tests/test_api.py` fails if they drift). Data hooks (`src/api/queries.ts`) key every query on `/api/status`'s `data_version`. The status is checked only when a new hour is due (`lib/schedule.ts`: the latest hour's end + 1 h + 8 min, server clock, per-visitor jitter; then 3 → 5 → 10 min apart while late; never under 2 min), so a visitor costs about one request an hour. The query cache lives for 6 h in memory and is saved to localStorage (`lib/persist.ts`, current data version only, dropped on a new build): switching pages or reloading asks the server nothing. Controls live in the URL (`useParam`), and each page's last settings are remembered per browser (`lib/rememberSettings.ts`) for the menu links and later visits. Pins: TypeScript 5.9 (openapi-typescript needs 5) and TanStack Table v8.
- **Design rules** (`web/src/index.css` tokens): two themes, Dusk (dark, the default) and Parchment (light), switched in the header and remembered per browser (`lib/theme.ts`; `index.html` applies it before the first paint). Every colour comes from a token, shadows too (`shadow-shadow/40`), so both themes work; never hard-code a colour. Fraunces for page and section titles, Nunito Sans for everything else (bundled with `@fontsource`). Green and red mean profit and loss and nothing else; the accent (apricot / copper) is the brand. Money columns first, numbers right-aligned in tabular figures, long names truncated with a tooltip. Charts: ECharts, lazy-loaded, UTC axis, lines break at missing hours (`lib/chartOptions.line`), linear with log as an opt-in. Every page handles no data (503), waiting for first trades and a stale feed. Check phone width (375px) with real device emulation, since headless Chrome won't size a window that narrow.
- **Deploy:** one `Dockerfile`, three Railway services (`deploy/railway/`): web (uvicorn serving `/api` + `web/dist`, hashed assets cached for a year, served pre-gzipped), Postgres, and the pipeline (`eb pipeline run` on an hourly cron, writing Postgres directly, then syncing the Supabase backup; no volume). The image bakes in DuckDB's postgres extension and runs as a non-root user. `deploy/cloudflare/` holds the fallback-page Worker for Cloudflare (the app stamps `X-EB-Origin: app` on every response for it; `node --test "deploy/cloudflare/*.test.mjs"`). Abuse protection (the Worker's method/body screen and per-address limit, `api/guard.py`'s origin key and per-visitor limit, docs off in the image) is in `docs/security.md`. `deploy/railway-sim/` runs the whole project locally with Railway's billing (`run.py`; never reaches the real servers: the pipeline only sees an upstream stand-in serving pages on disk).
- **Same answers on both engines:** text sorts happen in polars, not SQL `ORDER BY` (Postgres sorts by locale); rankings break ties by `item_id`. `tests/test_postgres.py` compares every service and endpoint.

- **Through `site_writer`, whole-table statements run on Postgres** (`db.pushdown(con)`): DuckDB's postgres scanner answers a DELETE, an aggregate or a correlated subquery by copying the league's rows out (~100 MB a pass: slow, and billed egress across providers). Pass `db.pushdown(con)` to rows / scalar / frame / execute for plain-Postgres SQL on site tables; `tests/test_pipeline.py` fails if a pass copies a big table unfiltered.
- **`services/` SQL must stay Postgres-compatible.** No `GROUP BY ALL`, no DuckDB-only functions. The loaders in `normalize/` run locally on DuckDB (they `read_parquet` etc.), so they're exempt. `storage/schema.sql` must run on both engines (`DOUBLE PRECISION`, `ON CONFLICT`, `ADD COLUMN IF NOT EXISTS`). New columns are appended as `ALTER TABLE … ADD COLUMN IF NOT EXISTS` *after* the table's `CREATE`.
- **DuckDB 2.0:** an `execute()` result stays open until fully fetched. Use the helpers `db.rows` / `db.scalar` / `db.frame` (`storage/db.py`), never `fetchone()` on a connection. The same helpers take a psycopg (Postgres) connection, translating `?` placeholders, and they feed the opt-in query meter (`db.metered()`). Reads that bypass them are invisible to the performance tests. Polars is 2.0 too (e.g. CSVs are read positionally with an explicit header check).
- **Resumability is by construction:** every output is written to a temp path and renamed (`ingest/files.py`, `.part` + HTTP Range/If-Range for downloads), so a finished file is its own completion marker. Each league loads in one DB transaction. Exchange loads are **incremental** (`exchange_hour_loaded` tracks loaded hours; a load adds new hours and deletes only hours that left the window), so the database is never wiped to add data. The dump loader skips unchanged inputs via the `ingest_load` fingerprint. Bump a loader's `*_VERSION` constant when its output changes; that triggers one full rebuild.

**Data sources and how they become rows.** The source is in `price_observation.source`.
- `poe.ninja-dump`: daily, every challenge league since 2016 (`ingest/poe_ninja_dumps.py` → `normalize/dump_loader.py`). Only currency, divination cards and uniques are loaded; no base items or gems.
- `ggg-exchange-hourly`: GGG's public currency-exchange history, one immutable page per hour across all leagues, since Settlers (`ingest/currency_exchange.py` → `normalize/exchange_loader.py`). An hour is published a few minutes after it ends. Page `T` must return `next_change_id == T+3600`; earlier timestamps silently return the first page, so every page is validated. The loader prices items by volume-weighting their Chaos and Divine legs (Divine rate carried forward) and also writes `cross_market_hour` (every Chaos-market hour, with the same-hour Divine leg when there is one; loops must filter to `cross_market.BOTH_LEGS`).
- **Item identity:** uniques are `ninja:<poe.ninja Id>` (stable across leagues). Everything currency-like, cards included, is `currency:<slug of name>` in every source. Exchange items are named from RePoE by GGG metadata id. An ambiguous RePoE name never merges items: it becomes `Name (MetadataName)`. A name shared only with a legacy non-stackable id or a Tencent-realm copy isn't ambiguous for the stackable id the exchange trades (`exchange_loader.ambiguous_ids`); classic fragments and breachstones rely on this.
- **Hosting scope:** live-league data only, plus the Launch history (`launch_history`: each finished league reduced to its window medians, ~2.5k rows a league; `services/launch_picks.capture`). Past leagues' hourly rows are local, for research.
- **Windows:** `exchange sync` loads a league's first 14 days. `live` loads the launch fortnight **plus** the latest 14 days (`Window.keep_launch_days`), and finds an unknown launch hour by binary search (`find_launch`). Launch-oriented views limit themselves to `day_offset < 14`.

**Curated mappings** (rebuilt after every load by `normalize/mappings.refresh_mappings`):
- `tracked_item` groups (currency / essence / scarab / divination) are name rules in `normalize/tracked.py`, limited to the **core drop pool** (`ingest/core_pool.py`). The pool is poe.ninja's *current-league* exchange lists (`core_pool.SOURCES`: the currency group is the Currency list, Catalysts included, plus Fragment and Oil), one snapshot per list, replaced (never merged), plus overrides in the committed `config/core_pool.toml` (`exclude` global, `[include]` per group).
- `divination_card`: cards are followed only if NeverSink's loot filter shows them (`ingest/loot_filter.py`, tiers t1–t4). Set size and reward come from RePoE (`normalize/divination.py`). `reward_item_id` is set only for fixed currency/card rewards. Random currency rewards are priced at their floor, the cheapest item they can roll: the pools in `config/card_rewards.toml` become `card_reward_pool` on each load (`normalize/card_rewards.py`, finding 12).

**Analysis and scoring.** `analysis/launch_patterns.py` holds the phase-2 tools: unique moves by tier, relative launch curves using a median day-1 baseline, group timing, and card turn-ins across leagues. They report per league, newest first, with recency weights (half-life in leagues). `services/scoring.rank_score` is the one opportunity score: percentile rank per factor, then a weighted mean. Card flips, cross-market loops and the live view all use it. Turn-in figures use the median hour, because thin markets have junk hours.

## Hosting plan and cost rules

Target: everything on Railway Hobby ($5 a month including $5 of usage): web, Postgres (only what the site reads: the live league, its window's pages and the Launch history) and the hourly pipeline cron, plus the off-site backup on Supabase's free tier (**`docs/supabase.md`** when setting it up: the connection string, what's there, the limits). The go-live checklist is `docs/go-live.md`. Simulated with the (since retired) Farming page, 10 and 100 daily visitors use $2.72 and $3.73 of usage a month, ~$4.9 estimated at 1000 (`docs/hosting.md#the-railway-bill`), mostly always-on memory, so watch for anything that scales cost with time or traffic:
- **Never rewrite data to add data.** Loads stay incremental: insert new hours, delete only what leaves the window.
- **Pages must read small results.** Do aggregation in SQL or in precomputed summary tables written by the pipeline, not by pulling raw hourly rows into Python. Memory, CPU and egress are what cost money on Railway. Summaries are computed in SQL (`cross_market.summarize`, `divination.turn_in_summary`, `launch_patterns._curves_sql` / `group_curves`) with Postgres-compatible medians (`percentile_cont(0.5) WITHIN GROUP (ORDER BY …)`, `FILTER (WHERE …)`). The landing page (Market recap, `services/missed.py`) filters by time in SQL (`since=`), sends all its look-backs in one small cached response, and caches on the latest loaded hour, not a timer. Don't divide by a column without `nullif(…, 0)` (Postgres raises on division by zero). Filter the big tables by `league_id`, never by a joined `league.name`: use `= (SELECT id FROM league WHERE name = ?)` for one league, or `services/leagues.ids()` plus `IN (?, …)` for several. Otherwise Postgres can't seek the (league, time) indexes (`IN (SELECT …)` becomes a hash semi-join).
- **Store only what the site reads.** This is a standing practice, not a one-off fix. Before adding a table, column or data source, or loading more of an existing one, check which page or feature reads it, and keep only that. Measure it: rows stored vs rows actually read. Keep whole datasets only where the feature needs the whole universe.
  - Today: hourly price rows are kept only for price-mapping items, followed cards' rewards, and Chaos and Divine (`exchange_loader._keep_used_items`). `cross_market_hour` stays complete because it *is* the arbitrage universe.
  - When a feature needs more, widen the keep rule deliberately and rebuild with `--force`, rather than storing everything "just in case".
  - The same goes for reads: return summaries from SQL, not raw rows.
- **Serve tables from the cache, never per request.** An endpoint builds a `View` (`api/deps.py`): computed once per data version, stored as JSON bytes gzipped once, sent to every visitor with an ETag (`304` for a client that has it). The data version is read at most every 15 s, so a cached request makes no database query. The pages' default views are precomputed when new data loads (`api/warm.py`; `default_views` must match what the frontend sends, which `tests/test_api.py` checks). The caches are bounded LRUs that compute each key once however many requests wait for it (`api/cache.py`); Price check's items are `slim` views in their own cache, kept as gzipped bytes only. The pages send the data version as `?v=` on every table request (ignored by the server) so browser and Cloudflare caches never mix hours; `/api` responses without their own Cache-Control are `no-store`, and Cloudflare's edge caches the rest as the header allows (`deploy/cloudflare/`). The API reads settings through `deps.settings()`, not `get_settings()` per request (~0.5 ms each). A view that changes less often than the data (the Backtest report) has a `stamp` (its build time): a new hour reads only the stamp and keeps the cached bytes and ETag.
- **The API serves only what the pages request** (`/api/status`, `/api/missed/{league}`, `/api/launch/picks`, `/api/backtest`; Price check's endpoints are being built, docs/price-check.md), all precomputed each hour (plus the usage beacon `POST /api/hit`, one event from a fixed list counted in memory, and the owner's `/api/stats` behind `EB_ADMIN_TOKEN`: `docs/usage.md`), so visitors never make it read the database: no endpoint takes free-form arguments, since each new combination would be computed from the database (load anyone could run up). `tests/test_api.py` fails if a route is added. The other exception is the owner's admin page (`/api/admin/*`, `api/routes/admin.py`, docs/admin.md): `/api/stats` and it are behind `admin.require_admin` (`EB_ADMIN_TOKEN`; 404 when unset), `no-store`, read per request since only the admin calls them. A page that needs one adds it with its precomputed default and a bounded set of arguments.
- **Units are converted in the browser.** Live tables come in Chaos only; `/api/status` carries each league's latest Divine price (`divine_chaos`) and the page converts (`lib/format.inUnit`). One cached table per view instead of one per unit, and switching units makes no request.
- **Index for the access paths.** `schema.sql` indexes league + source + time, because the primary keys start with item id.
- **What to fetch is decided by the database, not the disk** (`exchange_loader.needs_rebuild` / `loaded_hours`), not by which pages are stored. Reference data (RePoE names, core-pool snapshots, loot-filter tiers) lives in `reference_data` (`ingest/reference.py`). **Never download data we already have:** market hours are immutable and fetched once; reference sources go through `reference.fetch_if_changed`, which checks at most every `max_age` (RePoE weekly, pool and tiers daily; `eb exchange sync --refresh` checks now) using conditional requests (stored ETag / Last-Modified), so an unchanged source answers 304 and nothing is downloaded.
- **The full list** of known cost issues and performance findings, with their status, is in `docs/hosting.md`.
- **Performance is measured, not guessed.** CI (`.github/workflows/ci.yml`) runs lint, all tests and a Postgres 17 job. `tests/test_performance.py` budgets each page's reads, checks that live pages don't read more as history accumulates, and checks each live update's requests and writes (via `ingest_run`). When a change legitimately needs more, raise the budget in the same change and say why. Perf tooling stays local or in CI; nothing goes on the public site (a server-side dev panel later, if needed).
- **Trade / Research split (in progress):** the site is splitting into a **Trade** section and a **Research** section with preloaded data and graphs. The Backtest has moved to Research (`/research/*`, `components/Research.tsx`, its pages listed in `lib/research.ts`); build further steps only as the user approves them.

## Scope rules (decided by the user)

- **Challenge leagues only.** Event and Ruthless leagues are excluded from data and analysis; every command defaults to `kind = challenge`.
- **Only show items in the current core drop pool.** Remove an item via `config/core_pool.toml`, not code.
- **Uniques are out of scope** (2026-10-25): their prices follow each league's popular builds, and the rest are mostly gambling uniques. No unique features, no poe.ninja live poller, no unique card rewards; don't propose them. The daily dumps still load uniques (existing data only).
- **Design for a new league's data arriving.** At launch everything is null and fills in hour by hour, with gaps (no Divine rate in the first hours, untraded items, a single league loaded). Every page must handle no data, one hour, partial days and one-league states. Widgets with data-dependent ranges must not break when there's only one option.
- Recent leagues are the best reference; the currency exchange (Settlers, 2024-07) is a structural break.
- Charts default to linear axes (log scale is only an opt-in toggle). Trading tables put the money columns first. Credit poe.ninja (CC BY-SA) on the public site.

## Testing patterns

- **Tests never touch `data/`.** `tests/conftest.py` points `EB_DATA_DIR` at a temp dir at import. Code that takes `settings` must still use `settings.db_path` for every session, never the default path.
- **A new service or analysis query goes into `_cases` in `tests/test_postgres.py`**, so it's compared between DuckDB and Postgres. Queries behind the live pages also go into `LIVE_QUERIES`, which checks their index use. Text ordering differs between the engines (Postgres sorts by locale), so sort name lists in Python, and don't select a column twice.

- Exchange behaviour is tested with `FakeExchange` / `market()` / `client_for()` in `tests/test_currency_exchange.py` (other test modules import them). `FakeExchange.now` marks the hour still being traded (end of stream).
- The API is tested with FastAPI's `TestClient` on the replay fixture (`tests/test_api.py`: every endpoint after every update). `conftest.py` resets the API caches and sets the version TTL to 0 for each test. The frontend has Vitest + Testing Library tests against a stubbed `fetch` (`web/src/**/*.test.ts(x)`), covering each page's no-data / waiting / stale states.
- `tests/test_live_pipeline.py` replays real GGG pages (Mirage's first 30 hours, `tests/fixtures/mirage_launch.json.gz`) through `ingest.live.sync_live`, hour by hour, and checks what the API reports after each hour. Regenerate the fixture with `python tests/fixtures/make_fixtures.py` (needs Mirage data in `data/`).

## Data and repo hygiene

- All data lives in the gitignored `data/` folder (the default `EB_DATA_DIR`, anchored to the repo root). Never commit it.
- Settings come from `EB_*` environment variables or `.env` (`config.py`).
- `.claude/` and `.agents/` are intentionally left untracked.
- The root `.gitignore` is Python's template, which ignores every `lib/`; `!web/src/lib/` re-includes the frontend's. Check `git add -n` for new folders.

## Working alongside other sessions

Several Claude sessions may work in this checkout at once, sharing one working tree and one git index. On 2026-10-23 one session's `git commit` picked up another's staged `git rm`, which broke `main` until it was restored. So:
- **Stage and commit only your own files, by path, in one step:** `git add <your paths> && git commit -m …`, or `git commit -m … -- <your paths>`. Never `git add -A`, `git add .`, `git add <whole folder>` or `git commit -a`.
- **Don't leave anything staged between turns.** Delete files with plain `rm` and stage the deletion only in the commit that needs it (`git add -u <path>`). Something you didn't stage may be sitting in the index: check `git diff --cached --stat` right before committing and unstage what isn't yours (`git restore --staged <path>`), leaving the file itself alone.
- **Leave other changes alone.** Modified or new files you didn't touch belong to someone else's work in progress: don't commit, revert, format or delete them, and don't run formatters over the whole repo when others' files are dirty (format your own paths). If your change needs theirs, say so instead of committing it.
- **For long or wide changes, use your own worktree:** `git worktree add ../eb-<task> -b <task>` and merge back, so nothing is shared. Remove it when done.
- **Before pushing,** `git fetch` and look at `git log origin/main..main`: say which commits are yours, never push someone else's unreviewed work as part of yours without saying so, and never force-push `main`. A broken commit that's already pushed gets a fixing commit, not a rewrite.
